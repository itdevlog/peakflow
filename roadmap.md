## 🔴 Критические баги (исправить в первую очередь)

### 1. «✏️ Исправить последний» не работает для родителей
- **Где:** `bot.py:430` → `edit_measurement(DB_PATH, mid, new_val, callback.from_user.id)`
- **Суть:** `edit_measurement()` (`database.py:101`) обновляет запись только при совпадении `user_id` записи (= `CHILD_ID`) с переданным ID. Родитель передаёт свой ID → `rowcount = 0` → всегда «❌ Не удалось изменить запись». Для ребёнка работает.
- **Фикс:** передавать `CHILD_ID` (как уже сделано в `_save_edit_any`, `bot.py:452`), либо добавить функцию родительского редактирования в `database.py`. Покрыть регрессионным тестом (см. №27).

### 2. `mark_reminder_sent()` стирает другие флаги дня
- **Где:** `database.py:284-287`
- **Суть:** `INSERT OR REPLACE INTO reminders_sent (date) VALUES (?)` пересоздаёт всю строку, сбрасывая соседние флаги в 0. Пример: утренний флаг поставлен в 10:00, вечером недельный отчёт делает REPLACE — флаг утра теряется. В прод-БД 114 дней истории — искажения уже возможны.
- **Фикс:** `INSERT ... ON CONFLICT(date) DO NOTHING` + отдельный `UPDATE ... SET <type> = 1`.

### 3. Планировщик может пропустить напоминание на весь день
- **Где:** `bot.py:1126, 1143, 1159`
- **Суть:** условие `hour == DEADLINE and minute == 0` при `sleep(60)`: если тик пришёл в 09:59:59, следующий будет ~10:01:00 — окно закрыто, напоминание молча не уйдёт.
- **Фикс:** проверять `minute < 2`, либо хранить время последнего тика и ловить «пересечение границы часа», либо APScheduler.

### 4. Двойной `callback.answer()` → риск TelegramBadRequest *(перечень уточнён!)*
- **Суть:** хендлер вызывает `await callback.answer()`, затем `respond()`/`answer_callback()` вызывает `answer()` второй раз на тот же query. Если Telegram отклоняет повторный ответ, `callback.message.answer()` **не выполняется** — пользователь не получает экран. `answer_callback` не оборачивает `answer()` в try/except (`bot.py:142-147`).
- **Затронуты (проверено построчно):** `cb_add` (316→324/338), `cb_add_force` (348→352), `cb_history` (539→569), `cb_history_page` (546), `cb_settings` (672→676), `cb_export` (763→768/804), `cb_chart` (871→877/925), `cb_summary` (939→968), `cb_stats` (1043→1064).
- **⚠️ Уточнение к прошлому аудиту:** `cb_weekly` НЕ затронут (после `answer()` шлёт через `message.answer`, без второго ответа на query). Прошлый аудит его указывал ошибочно; зато пропускал add/history/settings.
- **Фикс (минимальный):** в `answer_callback` обернуть `await callback.answer()` в `try/except TelegramBadRequest: pass`. Правильнее — убрать дубли: `answer()` только в одном месте.

### 5. `del_confirm_*` без проверки прав
- **Где:** `bot.py:614-629`
- **Суть:** `cb_delete` проверяет `is_parent()`, а подтверждающий хендлер — нет. Защита должна быть на этапе выполнения действия, а не показа кнопки.
- **Фикс:** добавить `is_parent(callback.from_user.id)` в `cb_delete_confirm`.

## 🟠 Надёжность и корректность данных

### 6. Молчаливая перезапись времени суток
- **Где:** `bot.py:369-370` (`_save_measurement`)
- **Суть:** если слот `auto_time_of_day()` занят и `forced_tod` не задан, замер молча записывается как противоположное время суток. Замер в 10:30 при существующем утреннем попадёт в БД как «Вечер» → искажает статистику утро/вечер и недельные сравнения.
- **Фикс:** разрешать несколько замеров одного времени суток (счётчик вместо булевой логики «есть/нет») — частично уже реализовано через `add_force_`, но авто-путь всё ещё инвертирует. Явный вопрос пользователю при занятом слоте.

### 7. Блокирующие вызовы в async-хендлерах
- **Суть:** все SQLite-операции и генерация matplotlib-графика (`bot.py:888-923`) выполняются синхронно в event loop. Соединение открывается **на каждый запрос** (+ `PRAGMA journal_mode=WAL`) — 8–10 соединений на одно действие пользователя. При росте объёма бот замирает для всех.
- **Фикс:** `asyncio.to_thread()` для тяжёлых операций; долгоживущее соединение или `aiosqlite`.

### 8. Небезопасный парсинг callback_data
- **Где:** `bot.py:547, 587, 616, 638, 476, 489`
- **Суть:** `int(callback.data.replace(...))` без `try/except` — неожиданный payload роняет хендлер (и, без CI/тестов, никто не узнает).
- **Фикс:** хелпер `parse_int()` с fallback + алерт «Запись не найдена».

### 9. Состояние FSM «залипает»
- **Где:** `bot.py:1091-1096` (`catch_all`), `bot.py:714`
- **Суть:** во время `pef_input_*` ввод текста молча игнорируется (`if current: return`). В `editing_target_pef` нецифровой ввод не матчится `F.text.isdigit()` — тоже молчание. Пользователь не понимает, что делать.
- **Фикс:** хендлеры «нецифрового ввода» для всех состояний: подсказка + кнопка отмены. Плюс `/cancel` команда.

### 10. Дрейф схемы БД — **подтверждено по прод-БД**
- **Факт:** в `peakflow.db` таблица `measurements` создана старым кодом: БЕЗ `CHECK(time_of_day IN (...))`, С колонкой `note TEXT` (кодом не используется) и `FOREIGN KEY (user_id) REFERENCES users(user_id)`; таблицы `users` (3 строки) и `parent_child_links` (1 строка) — legacy, кодом не используются. Текущий `init_db()` о них не знает. Миграции — через `try/except ALTER`, без версионирования.
- **Фикс:** `PRAGMA user_version` + явные миграции; legacy-таблицы либо использовать (см. Фаза 4, мультидет), либо задокументировать и вычистить.

### 11. Нет индексов + LIKE-запросы
- **Факт:** в прод-БД только автоиндексы PK; все выборки фильтруют `user_id` + `measured_at` через `LIKE 'YYYY-MM-DD%'` (`database.py:153, 164`) — индекс по префиксу LIKE всё равно не используется.
- **Фикс:** `CREATE INDEX IF NOT EXISTS idx_meas_user_time ON measurements(user_id, measured_at)`; заменить LIKE на диапазон `>= today AND < tomorrow`.

При этом `delete_measurement` и `get_week_measurements` нигде не используются (мёртвый код).
- **Фикс:** весь SQL — в `database.py`; добавить функции `get_measurement_by_id()`, `update_measurement_as_parent()`, `delete_measurement_as_parent()`; мёртвое удалить.

- **Где:** `config.py:11` и `database.py:7` — оба читают env напрямую. Правка одного не затронет другое. Ручное смещение не учитывает DST.
